# Sim2Real Measurement Results — 2026-09-23

**Robot:** humanoid_lite, legs only (12 joints, 2 CAN buses), host `nse-MINI-S`
**Policy under test:** `walk_smoothA-full_2026-08-25`
**Answers:** [docs/SIM2REAL_MEASUREMENTS.md](../SIM2REAL_MEASUREMENTS.md) — M1, M2, M3, M6, M8, B5

## 1. What to change in training, in priority order

| # | Change | Evidence | Confidence |
|---|---|---|---|
| 1 | **Penalise peak knee torque directly**, not just action rate | knees demand p95 **28 N·m** against a **26.9 N·m** physical ceiling; saturate 52% / 33% of ticks | high |
| 2 | **Shrink `joint_pos` observation noise** from U(±0.05) rad to ~**1e-4 rad** | measured floor **4.18e-5 rad**; trained value is ~**1200×** too wide | high |
| 3 | **Do not add a per-joint observation-delay stagger.** One uniform 0–10 ms delay term | age spread across joints **0.84 ms** standing, **0.30 ms** walking — 3–8% of the frame period | high |
| 4 | **Do not add a stale-hold / dropout term** | **0.00%** stale-hold in both regimes, across 720k + 213k frames | high |
| 5 | **Do not add a gyro bias term** (`NoiseModelWithAdditiveBiasCfg`) | unmeasurable on this IMU — see §7 | high |
| 6 | **Keep randomisation ranges tight; no thermal widening** | CPU 54–65 °C, zero throttle events, statistics flat across 10 min | high |
| 7 | Consider adding **encoder quantisation** at 1.023e-4 rad | measured exactly 1.00 count, uniform on all 12 joints | medium |

Items 2–6 are each a case of *removing* invented randomisation. Per Menlo's rule — only
randomise what is actually random — every one of these currently makes the policy hedge against
a distribution this hardware does not have.

## 2. The headline: raising the knee cap did not fix torque starvation

On 2026-08-24 the knee `torque_limit` was raised 6.0 → 11.0 N·m because the knees showed a
persistent static droop that saturated the 6.0 cap. `_CONTRACT_EFFORT` was updated to match
(`humanoid-policy` 11da97a). **That fixed the static problem and did not fix the dynamic one.**

Measured over the walk-attempt window (700 policy ticks), with torque reconstructed as
`tau = kp*(target - pos) - kd*vel`, kp=45.0 / kd=1.5 — the same method that produced the
original 6.0 N·m finding:

| joint | mean error | \|tau\| p50 | \|tau\| p95 | \|tau\| max | ticks at/over cap |
|---|---|---|---|---|---|
| `left_knee_pitch` | −0.208 rad | 11.7 | **28.0** | 33.1 N·m | **52.1%** |
| `right_knee_pitch` | −0.142 rad | 5.1 | **23.1** | 30.2 N·m | **33.3%** |
| `left_hip_pitch` | −0.057 rad | — | 17.1 | — | 13.0% |
| `right_hip_pitch` | −0.138 rad | — | 24.2 | — | 37.3% |

For comparison, the 6.0 N·m run measured mean error −0.136 / −0.198 rad saturating 38.7% /
45.1%. **Same droop magnitude, same or worse saturation, at nearly double the cap.**

### Static is fixed; dynamic is not

Splitting the two components explains why the raise looked right and still failed:

* **Static demand** = kp × mean error = **9.4 / 7.6 N·m**. Under the 11.0 cap. At the old cap it
  was 6.1 / 8.9 against 6.0 — saturated. The raise did exactly what it was intended to do.
* **Dynamic demand** — p95 **28 N·m**, peak **33 N·m**. Over the 11.0 cap, and over the motor's
  physical ceiling of `Kt · I_limit · gear = 0.08958 × 20 × 15 = 26.9 N·m`.

**The policy is commanding torque the actuator cannot physically produce.** Raising
`torque_limit` again cannot help: 26.9 N·m is all there is, and demand already exceeds it. This
has stopped being a limit-configuration problem and is now a gait problem, which makes it
training-side.

Note that Smooth A *is* the smoothness fix, and it still demands 28 N·m p95. The action-rate and
action-L2 penalties reduced peak demand (sim `actrate_rms` 0.357 vs baseline 0.480) but nowhere
near enough. **Recommendation: add a reward term on instantaneous joint torque magnitude
approaching the 26.9 N·m ceiling, rather than continuing to approach it indirectly through
action smoothness.**

## 3. Measured gait vs sim

`scripts/measure/gait_segment.py` classifies each second by knee excursion and left/right knee
correlation — alternating (negative) is stepping, in-phase (positive) is the torque-starvation
signature, near-zero excursion is standing.

```
t=  0- 22s  stand
t= 22- 76s  walk attempts — WALK and SAG alternating
t= 76-100s  SAG, 24s continuous, corr +0.92   <- collapse
t=100-177s  stand
```

| metric | hardware | sim (eval_plant_compare) |
|---|---|---|
| knee L/R correlation | **−0.64** | −0.84 … −0.92 |
| gait frequency | **1.05 Hz** | 1.5 – 1.6 Hz |
| total stepping | 22 s in bursts | continuous |
| in-phase (sagging) | 46 s, corr **+0.88** | — |

The robot does step, but slower and less cleanly alternating than sim predicts, and it collapses
into 24 s of sustained in-phase sagging at +0.88 — within noise of the +0.91 that the 6.0 N·m
starved configuration produced. **This is the sim2real gap, now measured rather than inferred.**

## 4. Signal-path measurements (M1, M2, M3)

Captured passively with `candump`; PDO4 payload decoded directly (position/velocity, LE f32 at
bytes 0–3 / 4–7). No daemon client — see §8.

| | stand (600 s) | walk (177 s) |
|---|---|---|
| frames | 720,313 | 212,771 |
| rate | 100.0–100.3 Hz | 100.0–100.3 Hz |
| interval mean | 9.97–10.03 ms | ~10.0 ms |
| interval p99 | 10.4–10.9 ms | — |
| **frame loss** | **0.1058%** (762) | **0.0395%** (84) |
| **sample age mean** | **4.78 ms** | **5.05 ms** |
| sample age p95 | 9.5 ms | — |
| **stale-hold** | **0.00%** | **0.00%** |
| age spread across joints | 0.84 ms | 0.30 ms |
| bus errors | none | none |

### M1 — frame loss exists but is benign

Losses are almost all single frames (20 ms gaps); exactly one double loss in 600 s. They are
**uniformly distributed in time** — binned into 10 s windows the count has std 3.8 against a
Poisson expectation of 3.6, so they are not driven by load, disturbance, or anything the policy
does. Loss is also **lower under walking load** (0.0395%) than standing (0.1058%), which rules
out bus contention as the cause.

There is a consistent split: `left_hip_pitch`, `right_hip_yaw`, `right_hip_pitch`,
`right_knee_pitch` lose ~0.025%, the other eight lose 0.12–0.18%. Unexplained, and not worth
chasing — see the next point.

### M3 — dropouts never reach the policy

**0.00% stale-hold on every joint in both regimes.** The policy runs at 25 Hz against a 100 Hz
feed, so each tick has ~4 frames to choose from; a single lost frame still leaves fresh data.
The loss is real at the transport layer and completely invisible at the observation layer.

**No stale-hold or refresh-period term is needed in training.** This is measured, not assumed.

### M2 — one delay term, no stagger

Sample age is a uniform 0–10 ms distribution (mean 4.78, p95 9.5), exactly as expected for a
25 Hz consumer of an asynchronous 100 Hz feed. Spread of the per-joint means is 0.84 ms standing
and 0.30 ms walking — 3–8% of the 10 ms frame period.

**There is no poll-slot structure on this robot.** Asimov's per-group staleness model does not
transfer: they have a different bus layout. Model a single uniform 0–10 ms observation delay
applied to all 12 joints.

## 5. M6 — encoder resolution and noise floor

Quantisation is analytically `2π / 4096 / 15` = **1.023e-4 rad** (0.0059°), identical on all 12
joints, and measures exactly **1.00 count**.

**Noise floor: median 4.18e-5 rad (0.409 counts), max 0.599 counts across joints.**

> ### Methodological warning — do not detrend a long capture linearly
>
> A whole-window linear detrend over 600 s returns **5–50 counts** per joint. That number is
> wrong. A standing robot drifts and re-postures over minutes, and all of that real motion stays
> in the residual. The first version of this analysis reported it, and it would have become a
> training noise scale ~100× too large.
>
> The floor must be measured in windows short enough that genuine motion is negligible — 0.2 s
> (20 samples at 100 Hz) — taking the **median** across windows so a transient postural
> correction cannot inflate it. `scripts/measure/analyse.py` now reports
> `pos_noise_floor_*` and names the old figure `pos_residual_incl_drift_*` so the two cannot be
> confused.

**The trained `joint_pos` noise of U(±0.05) rad is ~1200× the measured floor.** Even Asimov's
±0.01 rad would be ~240×. This is the single largest correction available and it costs nothing.

Caveats worth carrying:

* Both `ankle_roll` joints read a floor of exactly 0.000 — their encoders never dither during a
  flat-footed stand, so this capture gives them no measurable floor.
* The operator applied intermittent pushes during the stand. Restricting to the quietest 25% of
  windows lowers the floor to ~0.28 counts, i.e. the pushes inflate it by 1.2–2.3×. Both figures
  are ~1000× below the trained value, so the conclusion is unaffected. The all-window figure is
  arguably the better one to train against, since it reflects the loaded, actively-correcting
  regime the policy actually runs in.
* `joint_vel` noise was not separately characterised; the firmware applies
  `velocity_filter_alpha = 0.7154` before the value is visible, so any figure describes the
  filtered signal.

## 6. M8 — thermal

Over the 600 s stand: CPU **54–65 °C**, and it **fell 9 °C** across the run (66 → 59). Both
`core_throttle_count` and `package_throttle_count` delta **zero**. Mean sample age was identical
between minute 0–2 and minute 8–10 (4.81 vs 4.80 ms).

**No thermal drift. Model tight distributions; do not widen ranges, and no cooling fix is
indicated.** (Menlo's thermal finding does not reproduce here.)

Caveat: buckets cover minutes 0–2 and 8–10 only. The 18–20 minute bucket needs a single 20 min
stand, which has not been run. Thermal behaviour is a hardware property, so one such run covers
all policies.

## 7. B5 — IMU gyro auto-zeroes at rest (M5 is unmeasurable)

The gyro is **healthy**. It clamps its output to exactly zero while stationary — an internal
resting auto-zero — and responds immediately to motion. Frames arrive at 99.78 Hz with zero
checksum failures; config registers are correct (CALSW 0x0000, RSW 0x025F with gyro output
enabled, 100 Hz, 921600 baud).

During the stand, from 21,492 real policy ticks:

| | all-axes-zero | max \|ω\| |
|---|---|---|
| all ticks | 2.74% | 1.920 rad/s |
| quietest 50% | 4.63% | 0.003 rad/s |
| quietest 25% | 6.45% | 0.002 rad/s |

`base_valid` was false on **zero** ticks. The deadband is very narrow — the sensor reports
genuine rates down to 0.002 rad/s — and never dominates while balancing.

**Consequences for training:**

* **No deadband term needed.** The gyro gives real rate feedback in the operating regime.
* **M5 (gyro bias / drift / Allan deviation) cannot be measured on this hardware.** The sensor
  suppresses exactly the signal M5 asked for; a 10-minute rest capture returns zeros, which is
  the clamp and not the bias. Per this project's own rule, **leave
  `NoiseModelWithAdditiveBiasCfg` off `base_ang_vel`** rather than populate it with a
  plausible-looking guess. Report it as an honest gap.
* A UI note for operators: the IMU panel's `● live` indicator is driven by `projected_gravity`
  alone and never inspects `angular_velocity`, and tilt/pitch/roll are accelerometer-derived.
  An accurate tilt readout is **not** evidence the gyro works.

## 8. Method, and what it is safe to conclude

**Capture path.** Everything is derived from a passive `candump` stream plus the policy's own
`StepRecorder` tick log. Nothing in `scripts/measure/` opens a daemon client.

> This is load-bearing, not stylistic. The daemon **broadcasts** telemetry to a single UDP
> destination (127.0.0.1:9000). UDP delivers each datagram to one bound socket, so a second
> client does not get a copy — it steals packets from the web service that runs the policy. An
> earlier telemetry-based sampler did exactly that on 2026-08-29: the policy's `base_valid`
> flickered false, the UI showed the daemon and IMU as dead, and a 10-minute run had to be
> aborted. `candump` takes a copy off the interface and cannot starve anything.

**Policy identification.** The bundle was confirmed by replaying 400 recorded observations
through every available `policy.onnx` and comparing to the recorded actions:
`walk_smoothA-full_2026-08-25` reproduces them with max absolute error **0.000000**; the next
closest bundle errs by 1.003. This was necessary because the status API stores the loaded
checkpoint internally but never exposes it, so neither the UI nor the operator can see which
policy is running — worth fixing.

**Control loop timing** is confirmed healthy: tick interval p50 40.02 ms, p95 40.99 ms against a
40 ms nominal. The recording's 17.9 Hz *average* is an artifact of three gaps (one 6.3 s) that
correspond to pauses between walk attempts, not loop stalls.

### Limitations — read before trusting any number above

1. **Torque is reconstructed, not measured.** `tau = kp*err - kd*vel` from logged targets and
   positions. The firmware additionally applies `torque_filter_alpha = 0.1454` and a feedforward
   term, so these are *demand* figures before clamping. The method deliberately matches the one
   that produced the original 6.0 N·m finding, so the comparison is like-for-like — but M7
   (commanded vs reported torque under a known static load) has **not** been run and would
   validate it directly.
2. **M2 uses a synthetic 25 Hz tick grid** in `analyse.py`. Valid for the age *distribution*
   because the policy loop and the PDO4 timers run on independent clocks. Real tick times are
   now available in the `StepRecorder` logs, so exact per-tick ages could be computed if the
   distribution ever looks suspicious.
3. **One policy only.** Baseline `walk` and `walk_smoothB-full` have not been captured. Nothing
   here compares policies; it characterises the hardware and Smooth A's demand on it.
4. **Operator disturbances during the stand** (intermittent pushes). Quantified in §5; affects
   only the M6 floor, and only by 1.2–2.3×.
5. **Walk sample is small** — 22 s of gait in bursts, one session. The torque finding is strong
   (52% / 33% saturation is not marginal) but a second walk capture would firm it up.
6. **M7 not run.** Needs a controlled static load and a commanded-torque sweep.

## 9. Reproducing this

On the robot PC, with a policy running:

```bash
# passive, read-only, safe alongside a live policy; stop anytime without losing data
scripts/measure/capture_run.sh <label>-stand 600 hold
scripts/measure/capture_run.sh <label>-walk  300 walk

# find the gait inside a capture that is mostly standing
python scripts/measure/gait_segment.py --capture docs/measurements/<...>_can.json
```

Set `HUMANOID_RECORD_DIR` on the policy process so `StepRecorder` logs tick data — the torque
analysis in §2 depends on it.
